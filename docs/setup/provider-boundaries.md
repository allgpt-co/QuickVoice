# Provider boundaries

QuickVoice boots its local development stack with the placeholder values in the tracked env templates (`*.env.dev.example`). Placeholder startup is not proof that provider-backed behavior works: the API, console, and AI service come up, but calls, purchases, deliveries, and retrievals only complete when they can reach a real external account.

This page maps each provider-backed feature to its env keys and consuming code paths, and records whether a local substitute exists today.

How to read the matrix:

- **Env keys** name variables in the tracked templates. Set real values in your ignored `.env.dev` files; never commit credentials.
- **Code paths** cite the files that consume those variables, so every row can be traced to current behavior.
- **Startup vs provider-backed behavior** states what happens with placeholders versus what the real action requires.
- **Local substitute** is only marked "bundled" when the repo ships it (a Compose service, adapter, or image recipe). "Not wired" means the integration is possible but needs code or an external service the repo does not include.
- No row below is a partnership, certification, SLA, or included account. Each provider requires an account you create, configure, and pay for with that vendor.

## Startup is not provider proof

A green `task up:dev` and a passing readiness endpoint only prove the local services started and env presence checks passed. The readiness checks in `apps/server/src/modules/system/readiness.service.ts` test whether variables are set — `READINESS_REQUIRED_INTEGRATIONS` can gate which of them must be present — but env presence does not prove the provider account is reachable, funded, or correctly configured. Use the row's code paths to trace exactly which action crosses the boundary before assuming a workflow works end to end.
